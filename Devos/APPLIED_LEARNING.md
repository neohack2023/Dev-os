# DevOS Applied Learning Spine

Status: **Candidate / research-backed**

Operating law:

> Experience may nominate a lesson. Independent evidence may strengthen it. Evaluation may demonstrate utility. Only governed promotion may make it durable operating knowledge.

## Learning spine

```text
OBSERVE
  ↓
NORMALIZE ATOMIC FINDINGS
  ↓
CROSS-REFERENCE CURRENT STATE
  ↓
RESOLVE LINEAGE + COLLAPSE DERIVATIVES
  ↓
TRIANGULATE INDEPENDENT ROOTS
  ↓
REFLECT / DIAGNOSE
  ↓
CONSOLIDATE EXPERIENCE
  ↓
UPDATE CAPABILITY GRAPH
  ↓
SELECT CURRICULUM TARGET
  ↓
GENERATE CANDIDATES
  ↓
EVALUATE FOR TRANSFER + REGRESSION
  ↓
STONE
  ↓
MASON
  ↓
PR + CI + CANARY
  ↓
POST-CHANGE RE-TRIANGULATION
  ↓
PROMOTE | REVISE | ROLLBACK | NO-OP
```

## Required distinctions

DevOS must keep observation separate from interpretation, prevalence from independence, reflection from truth, memory from authority, training success from transfer, candidate generation from promotion, and merged code from demonstrated improvement.

Evidence lineage should distinguish independent roots, reproductions/derivatives, partial shared inputs, and unknown lineage. Root count never changes authority by itself.

Reflection artifacts should state the observed failure, expected behavior, mechanism hypothesis, evidence for/against, alternatives, proposed lesson/scope, and a required disconfirmation test.

Useful memory representations are episodic (what happened), semantic (lesson supported across evidence), procedural (executable/retrievable skill), and negative (known failure/rejected strategy). Every evolved representation keeps immutable evidence/source references underneath it.

## Capability maturity

Suggested engineering maturity levels:

`RECALL → RECOGNITION → REFLECTION → TRANSFER → COMPOSITION → ADAPTATION → METACOGNITIVE_CONTROL`

These are engineering maturity states, not authority levels.

## Evaluation pyramid

```text
T0 hard invariants / deterministic regressions
T1 training fixtures
T2 development fixtures
T3 held-out transfer
T4 adversarial / counterfactual
T5 canary real work
```

The evidence that generated a candidate cannot be its only promotion evidence. Evaluators are versioned separately. Holdouts must not leak answers or implementation history. Riskier changes require stronger transfer and canary evidence.

Track a fitness profile rather than one universal score: correctness, held-out transfer, regression rate, abstention calibration, scope integrity, provenance integrity, authority integrity, determinism, context tokens, latency, cost, and review burden. Hard governance failures dominate performance gains.

## Governance boundary

```text
learning candidate
→ evaluation evidence
→ STONE package
→ MASON classification/write plan
→ authorized repo mutation
```

No optimizer, curriculum process, reflection layer, memory consolidator, or capability registry may mutate durable authority directly.

## Priority rule

Every learning experiment should accelerate an active project milestone, remove a repeated development failure, make a capability transferable, reduce context/evidence cost, or catch risk earlier. If none apply, it is not a DevOS priority.
